## 0. 一句话

后端现在是「**一个 Scene 演到底 + 边渲边切**」：渲染过程中每完成一个分镜就立刻产出该段的 mp4
并打一行事件到 stdout，前端可以真正实现「渲好一段播一段」，**且总耗时比过去的多进程方案还短**。

## 1. 后端最终方案（已完成）

### 1.1 用法

```bash
# 默认路径就是最优解，不需要任何开关
python generate.py examples/free_product_rule.json

# 仍保留的调试开关（比默认慢，只在单独调某个分镜时用）
python generate.py examples/free_product_rule.json --split
python generate.py examples/free_product_rule.json --split --jobs 2
```

### 1.2 实现要点

生成代码时在每个分镜边界插入 `self.section(n)`（`renderer.render(sections=True)`）：

```python
class StoryboardScene(Scene):
    def section(self, n):          # 分镜边界
        if n > 1:
            self._emit(n - 1)      # 合并上一段的 partial 片段 → mp4，并打印事件
        super().next_section("scene_%d" % n)
```

关键点：

- manim 的 partial 片段（每个 animation 一个 mp4）**是渲染过程中就写出来的**，
  所以在分段点当场合并即可，不必等 `finish()`
- 合并复用 manim 自己的 `SceneFileWriter.combine_files()`（PyAV remux，不重编码），8 段合计约 1s
- `generate.py` 用 `Popen` **逐行实时**读取 stdout
  ⚠️ 不能用 `subprocess.run(capture_output=True)` —— 它要等进程结束才返回
  ⚠️ 必须显式 `encoding="utf-8", errors="replace"`（见 §5 的 BUG-006）

### 1.3 实测数据

同一份 `free_product_rule.json`（8 分镜 / 480p15 / 20 核 Intel Ultra 7 255HX）：

| 方案 | 总耗时 | 首段可见 | 产物 |
|---|---|---|---|
| **最终（一个 Scene + 边渲边切）** | **13.7 s** | **2.3 s** | 整条 + 8 段 + 真实时长 |
| 默认 + `--save_sections`（等 finish 才切） | 12.9 s | 12.3 s | 整条 + 8 段 |
| 默认（完全不分段） | 12.9 s | — | 1 个 mp4 |
| 拆分渲染（8 个独立场景） | 16.1 s | 1.6 s | 8 段 |
| 旧 `--parallel`（8 分镜 × 8 进程） | 23.8 s | ~18 s | 8 段 |

**只比"完全不分段"多 0.8s，换来首段可见时间从 12.3s 降到 2.3s。**

实际输出：

```
[4/4] 渲染中（-ql，每个分镜渲完即出片）...
      [分镜 1] 已完成 5.0s    →  StoryboardScene_0000_scene_1.mp4  （累计 2.3s）
      [分镜 2] 已完成 7.333s  →  StoryboardScene_0001_scene_2.mp4  （累计 3.4s）
      [分镜 3] 已完成 8.0s    →  StoryboardScene_0002_scene_3.mp4  （累计 4.7s）
      ...
      [分镜 8] 已完成 8.667s  →  StoryboardScene_0007_scene_8.mp4  （累计 12.0s）
[OK] 渲染成功，耗时 13.0 秒
```

## 2. 产物契约（前端要按这个对接）

```
output/videos/{name}_scene/{quality}/
├── StoryboardScene.mp4              ← 整条成片
└── sections/
    ├── StoryboardScene_0000_scene_1.mp4   ← 第 1 段
    ├── ...                                 （共 N 段）
    ├── StoryboardScene_0007_scene_8.mp4
    └── index.json                          ← 真实时长索引
```

`index.json`（这是前端时间轴的数据源）：

```json
[
  { "index": 0, "video": "StoryboardScene_0000_scene_1.mp4", "duration": 5.0 },
  { "index": 1, "video": "StoryboardScene_0001_scene_2.mp4", "duration": 7.333 },
  { "index": 2, "video": "StoryboardScene_0002_scene_3.mp4", "duration": 8.0 }
]
```

> `duration` 是 manim 按**真实帧数**算出来的，比大纲 `durationSec`（设计值）准得多。
> **前端整片时间轴必须用这份数据**，否则分镜定位会漂。

### 渲染过程中的事件（stdout，将来转 SSE）

```
@@ {"section": 1, "video": ".../sections/StoryboardScene_0000_scene_1.mp4", "duration": 5.0}
@@ {"section": 2, "video": ".../sections/StoryboardScene_0001_scene_2.mp4", "duration": 7.333}
...
```

- 严格按 `section` 1→N **顺序**产出（单进程串行渲染）
- 后端接 SSE 时直接把它转成：

```
event: tool_result
data: {"index": 0, "url": "/media/.../s1.mp4", "durationSec": 5.0}
```

- `tool_done` 在进程退出后发，附整条成片 url

## 3. 前端改造清单

### 3.1 保留什么

### 3.2 改什么

| 项 | 现在 | 改成 | 状态 |

| 分镜片段来源 | 轮询 `scenes[].url`（`tool_result` 逐个到达） | 消费 `@@`/`tool_result` 事件流，**行为不变** | ✅ 无需改 |
| 分镜时长 | 大纲 `durationSec`（估算值） | `index.json` 的 `duration`（真实帧数） | ✅ 已改 |
| 缓冲编排器 | `firstReadyFrom()` 按 index 乱序重排 | **删除** —— 片段现在严格按 1→N 到达 | ✅ 已删除 |

| 渲染中状态 | 分镜一直显示"排队中" | 按 `tool_progress.step` 翻成"渲染中" | ✅ 已补 |

**实测（Mock，4 分镜）**：`tool_result` 的 index 为 `0,1,2,3` 递增，
`durationSec` 是真实帧时长 `5.199 / 14.333 / 10.733 / 6.667`（**不是**大纲的 `4.5/9/13/6`）。

> 注：前端原本并没有独立的"乱序编排器"文件 —— 所谓"编排"只是 `tool_result`
> 按 index 回填 `scenes[]`。现在行为不变，但**注释与文案**里"乱序是必然的"
> 结论已按本文件全部更正（`timeline.ts` / `playback.ts` / `PreviewPanel` / 落地页 / `web/README.md`）。

### 3.3 能新增的能力

因为首段 2.3s 就可见，可以实现此前放弃的体验（均已在现有组件里成立）：

- 整条渲完前就播第 1 段，后续段落渲好自动续上
- 进度条按"已就绪段落的真实时长"推进，未就绪部分显示为渲染中

### 3.4 前端的实现要点（改完后的样子）

```ts
// timeline.ts —— 时长来源的优先级：scene.durationSec 就是真实帧时长
// （确认阶段用大纲值占位，tool_result 到达后由 store 覆盖）
const duration = scene.durationSec ?? FALLBACK_DURATION;
```

```ts
// Workbench.tsx —— 串行渲染下 step 就是"已交付段数"，
// 所以正在渲的正是 scenes[step]（0-based）
if (stage === "rendering") {
  const cur = msg?.render?.scenes[step];
  if (cur?.status === "queued") patchScene(..., cur.index, { status: "rendering" });
}
```

**为什么覆盖时长不会让进度条漂**：串行交付下第 k 段到达时，它前面 k 段的真实时长
都已确定，第 k 段的 `start` 一旦算出就不再变 —— 只有它**后面**的格子会跟着挪，
而那些格子本来还是 pending。这正是"顺序交付"相比"乱序并行"省下来的复杂度。

## 4. 失败分层：什么错该在哪一层解决

**核心结论：JSON/语义层的错误不会走到渲染阶段，所以「重试」只用于兜环境错。**

```
① LLM 生成 JSON
   └─ schema.py / dsl.py 校验（带路径与原因）
      ✗ → 错误原样回灌给模型，最多 4 轮        ← JSON 类问题在这里解决
② 生成 Manim 代码
   └─ renderer._check_syntax() 用 compile() 兜底
      ✗ → 渲染器 bug（模板拼错），不是分镜问题
③ 渲染（manim 子进程）
   ✗ → 环境/代码问题 → 整条重跑（13.7s）
```

| 类别 | 例子 | 重试有用吗 | 处理方式 |
|---|---|---|---|
| **JSON / 语义错** | 引用未声明 id、颜色拼成 `BLUEISH`、duration 越界 | ❌ | **校验层回灌**（已有，`max_attempts=4`） |
| **静默失败** | 曲线无图例、步骤重叠、`\text{顶点}` 原样显示 | ❌ | 补 `schema.py` 规则 / 人工看画面 |
| **环境 / 代码错** | LaTeX 不在 PATH、GBK 解码崩、模板 KeyError | ✅ | 整条重跑 |

> `llm.py` 里对这条已有明确表述：
> "这些错误校验层已经能精确定位……把它们原样回灌给模型，模型几乎总能一次改对。
> **所以重试不是'再试一次碰运气'，是把校验层的确定性注入到模型的下一轮。**"

### 4.1 对架构文档 Q12 的修正

原设计「单分镜失败重试，绝不整条失败」在**串行模型下不再成立**：

- 一个 Scene 演到底，任一环节抛异常就是整条失败，不存在"重跑第 3 段"
- 但重试成本可控：**13.7s 整条重来**，比过去"重跑一段"（`--parallel` 时代）还便宜

建议改为：**失败可整条重试 + 重试成本可控（13s）+ 失败可定位到分镜**
（`_scene_code` 是按分镜生成的，异常能定位到具体分镜）

### 4.2 当前风险面很小

`eval/03-Bug清单.md` 记录的 7 个 bug **全部已修**。历史记录里会导致渲染进程失败的两条：

- **BUG-006**：中文 Windows 下 subprocess 未指定编码 → `UnicodeDecodeError`，读取线程崩掉、主流程卡死
  （注释原文：**"AI 侧沙箱 locale 是 UTF-8，所以 AI 跑不出这个 bug —— 环境相关 bug 只有真机才暴露"**）
- **BUG-007**：`HEADER.format()` 把代码模板里的花括号当占位符 → `KeyError`

## 5. 历史教训（避免重蹈）

2026-09-12 这轮排查先后走了两条弯路，**都比默认路径慢**：

1. 「每分镜一个进程」→ 8 分镜 18.0s（默认 12.3s）
2. 「拆分场景 + 进程内连渲」→ 8 分镜 14.6s

原因：

- **拆场景**：N 个独立场景 = N 次渲染器初始化 + N 次 `combine_to_movie`
- **多进程**：瓶颈是**内存带宽**不是 CPU。单进程 35.1 GB/s，8 进程并行时每个只剩 7.2 GB/s
  （整机约 58 GB/s 封顶），所以每个都慢 4~5 倍，20 个核帮不上忙

> **教训：遇到同类问题先读一遍 manim 源码（`scene_file_writer.py` 的 `section` / `combine_files`），
> 再动手造轮子。** 正确答案（partial 片段是渲染中逐个产出的）就在源码里。
