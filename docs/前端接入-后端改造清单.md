## 2. 把 print 换成事件（核心工作量）

### 2.1 结论：分镜片段已经在渲染过程中实时产出了

早期设想的做法是"拆分渲染 + `ThreadPoolExecutor + as_completed` 逐段 yield"。
**2026-09-12 实测后这条路线作废了**：拆场景比单场景慢，而且 manim 的 partial 片段
本来就是渲染过程中逐个写出来的，只要在分镜边界当场合并即可。

最终实现（`storyboard/renderer.py` 生成的 `StoryboardScene`）：

```python
class StoryboardScene(Scene):
    def section(self, n):          # 分镜边界，generate.py 插入 self.section(n)
        if n > 1:
            self._emit(n - 1)      # 合并上一段的 partial → mp4，并打印 @@ {json}
        super().next_section("scene_%d" % n)
```

`generate.py` 用 `Popen` 逐行读 stdout（**不能用 `subprocess.run(capture_output=True)`**，
它要等进程结束才返回），实时拿到：

```
@@ {"section": 1, "video": ".../sections/StoryboardScene_0000_scene_1.mp4", "duration": 5.0}
@@ {"section": 2, "video": ".../sections/StoryboardScene_0001_scene_2.mp4", "duration": 7.333}
...
```

实测产出（8 分镜 / 480p15 / 本机 20 核）：

```
[分镜 1] 已完成 5.0s    →  （累计 2.3s）     ← 首段 2.3 秒就可见
[分镜 2] 已完成 7.333s  →  （累计 3.4s）
...
[分镜 8] 已完成 8.667s  →  （累计 12.0s）
[OK] 渲染成功，耗时 13.0 秒
总耗时: 13.7s
```

产物：

```
videos/{module}/{quality}/StoryboardScene.mp4       ← 整条成片
videos/{module}/{quality}/sections/*.mp4            ← 每个分镜一段
videos/{module}/{quality}/sections/index.json       ← 真实时长索引
```

```json
[ { "index": 0, "video": "StoryboardScene_0000_scene_1.mp4", "duration": 5.0 },
  { "index": 1, "video": "StoryboardScene_0001_scene_2.mp4", "duration": 7.333 }, ... ]
```

→ 接 SSE 时，`tool_result` 的 `durationSec` **直接用这里的 `duration`**，
不要用大纲的估算值（那是设计值，和真实帧数有出入）。

### 2.2 SSE 怎么接：直接把 `@@` 行转发成事件

后端要做的就一件事：**流式读取子进程 stdout，把 `@@ {json}` 行转成 SSE 事件**。
`section` 事件天然对应前端的 `tool_result`：

```
event: tool_result
data: {"index": 0, "url": "/media/t123/v1/s1.mp4", "durationSec": 5.0}
```

`tool_done` 在进程退出后发（附整条成片 url）。`tool_progress` 可选：
按"已交付段数 / 总段数"推进，前端进度条就够了。

⚠️ 不要再走"拆场景 + 多进程"那条路（早期方案），原因见 §2.3。

### 2.3 为什么别拆场景、别开多进程

这一节最初设想是"每个分镜一个进程并行渲染"。2026-09-12 一轮实测把整条路都推翻了。

**结论：分镜级产物 manim 原生就有，不需要拆场景。**

本机实测（`free_product_rule.json`，8 分镜，480p15，20 核 Intel Ultra 7 255HX）：

| 路径 | 总耗时 | 首段可见 | 产物 |
|---|---|---|---|
| **默认（一个 Scene + 边渲边切）** | **13.7 s** | **2.3 s** | 整条 + 8 段 + 真实时长 |
| 默认 + `--save_sections`（等 finish 才切） | 12.9 s | 12.3 s | 整条 + 8 段 |
| 默认（完全不分段） | 12.9 s | — | 1 个 mp4 |
| 拆分渲染（8 个独立场景） | 16.1 s | 1.6 s | 8 段 |
| 旧 `--parallel`（8 分镜 × 8 进程） | 23.8 s | ~18 s | 8 段 |

**拆场景为什么慢**：N 个独立场景 = N 次渲染器初始化 + N 次 `combine_to_movie`
（每次都把同名的 partial mp4 重新合并一遍）。"一个 Scene 演到底"这些只做一次。

**多进程为什么没用**：瓶颈是内存带宽而不是 CPU ——

```
单进程内存拷贝吞吐      35.1 GB/s
8 进程并行（每个进程）   7.2 GB/s     ← 整机约 58 GB/s 就封顶
```

manim 渲染是内存密集型负载（逐帧 numpy + cairo 像素缓冲），8 进程并行时整机带宽
只从 35 涨到 ~58 就封顶，每个进程只剩 7.2 GB/s，全部慢 4~5 倍。
对照：8 进程做纯计算每个都满速；8 进程写 3200 个小文件 0.35 s；8 进程 import manim 1.14 s。

**前端要用的真实时长**：`sections/index.json` 里每段是按真实帧数算的
（`5.0`、`7.333`、`11.599`…），比大纲里的估算值准 —— **整片时间轴应该用这份数据**，
分镜定位与进度条会精确得多（见前端架构设计 §5 → `tool_result` 的 `durationSec`）。

> 教训：遇到同类问题先翻一遍 manim 的 CLI 选项和 `scene_file_writer.py`，再动手造轮子。
> 我们先后写了两版（多进程、拆分场景 + 进程内连渲），都比默认路径慢。
> 保留的 `--split` + `render_worker.py` 只用于"单独调试某个分镜"。

⚠️ **片段是按分镜顺序到达的**（不再是乱序）。

早期方案用多进程并行，片段必然乱序，前端得写缓冲编排器按 index 重排。
现在后端是单进程串行渲染 + 边渲边切，`@@ {"section": N}` 一定是 1,2,3…N 递增，
前端按序消费即可，**那条缓冲编排器可以直接删掉**。

## 3. 新增两个字段：`brief` 和 `outline`

现在 `free_pythagorean.json` 的顶层只有 `title / problem_type / _note / scenes[]`
（实测 4 分镜 4831 字符），**没有任何文字回答或大纲**。

### 3.1 改 schema

`storyboard/schema.py::validate()` 的 `out` 字典里加：

```python
out = {
    "title": ...,
    "problem_type": ...,
    "brief": str(storyboard.get("brief", ""))[:500],        # 新增：文字回答
    "outline": storyboard.get("outline") or [],             # 新增：大纲
    "intent": storyboard.get("intent", "propose"),          # 新增：propose / none
    "scenes": [],
}
```

`brief` / `outline` 校验要宽松（允许缺失），但 `scenes` 保持原来的严格。

### 3.2 改 prompt

`storyboard/llm.py::build_system_prompt()`：

```
输出结构（按顺序，字段顺序很重要 —— 前端靠流式顺序做到"秒级见字"）：
{
  "brief":    "用 2-3 句话直接回答这道题",
  "intent":   "propose" | "none",
  "outline":  [{"id":1,"title":"...","durationSec":4.5,"summary":"..."}],
  "scenes":   [ ...原有分镜... ]
}

字段顺序必须是 brief → intent → outline → scenes，不要调整。
intent 规则：适合用动画讲解的题取 "propose"；
纯概念问答（如"什么是直角三角形"）取 "none"，此时 outline 和 scenes 都给空数组。
```

**为什么强调字段顺序**：这样流式输出时 `brief` 最先到（1–2 秒），
前端立刻有字可显示，不需要把 LLM 拆成两次调用。现有的"校验失败回灌重试"逻辑**完全不用改**。

## 4. 复用 task 目录 = 白捡的增量渲染

`render_parallel()` 里已经有：

```python
same_src = os.path.exists(py) and open(py, encoding="utf-8").read() == src
if same_src and os.path.exists(seg):
    cached += 1
    continue
```

只要**修正时复用同一个 `name`（task 目录）**，`output/_parts/<name>/` 里的旧片段还在，
源码未变的分镜会自动跳过渲染。

所以"用户说把第三步讲慢一点 → 只重渲第三步"这个能力**不需要额外实现**，
只要保证：

```python
name = f"{thread_id}_{message_id}"      # 首次生成
# 修正时：同一个 name，旧片段保留
```

⚠️ 注意清理策略：task 目录会持续增长，需要定期清理超过 N 天未访问的。

## 5. 整分镜替换（对应前端 Q16）

不要用文本 patch 改 JSON（分镜内部 `duration` 与 `timeline.run_time` 耦合，
只改一处会改出"动画演完干等"的半吊子结果）。改为让模型重新输出**一个完整的分镜对象**：

```python
# api/routes/storyboard.py
@router.post("/storyboard/replace-scene")
async def replace_scene(req: ReplaceSceneRequest):
    sb = load_storyboard(req.thread_id, req.message_id)
    old_scene = sb["scenes"][req.scene_index]

    # 只把"要改的这一个分镜 + 指令 + 全局约束"喂给模型
    new_scene = await llm.regenerate_scene(
        instruction=req.instruction,
        scene=old_scene,
        context={"title": sb["title"], "total": len(sb["scenes"])},
        max_attempts=3,      # 复用现有的校验回灌重试
    )
    # 单分镜校验：dsl.validate_scene 本来就是逐个校验的，直接复用
    validated = dsl.validate_scene(new_scene, old_scene["id"])

    sb["scenes"][req.scene_index] = validated
    save_storyboard(req.thread_id, req.message_id, sb)

    # 复用同一 name → same_src 缓存自动跳过其余分镜
    return render_parallel_streaming(sb, name_of(req.thread_id, req.message_id), ...)
```

## 6. 并发与队列（别等到崩了才做）

单条 8 分镜任务峰值会吃满 `min(8, CPU核数)` 个核。**多个用户同时请求会直接打爆机器。**

MVP 最小方案（不引入 Celery）：

```python
# api/jobs.py
import asyncio
from asyncio import Semaphore

_render_sem = Semaphore(2)          # 同时最多 2 个渲染任务

async def with_limit(coro_factory):
    async with _render_sem:
        return await coro_factory()
```

再配一个 Redis 计数器做每日配额（对应前端 Q10）。

> 生产化时再换 Celery / RQ + 独立渲染 worker，MVP 用信号量足够。
