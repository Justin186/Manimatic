## 1. 图片输入：从"插件"并进 core（本次最大的一件事）

### 1.1 背景

同事发来一份 `plugins/` 参考实现（5 个功能），其中 `vision_input` 是图片输入。
它是**旁路插件**形态：独立端点 `/api/vi/chat`，靠换一条 uvicorn 启动命令启用，
宣称"`api/` 与 `storyboard/` 一个字节都不改"。

### 1.2 为什么最后没走插件（结论 + 证据）

**接入当天那句"零改动"就破了**，原因是三条具体的：

1. **复刻必然漂移，而且已经漂了。** 插件的 `generate.py` 是 core 里
   `stream_storyboard()` 那套「生成 → 校验 → 回灌重试」的**完整复刻**（约 200 行）。
   搬过来时和 core 比出 3 处分歧：硬编码 `temperature=0.2`（会让设置页改的温度静默失效）、
   漏了 `meta.storyboard`（多轮"改这一版"会丢上一版画面）、漏了 `diff_scenes` 对账。
   插件自己的注释就写着"复刻的代价是**流程会漂移**（上游改了重试策略，这里不知道）"
   —— 这不是意外，是这个结构的必然后果，而且漂移**是静默的**。

2. **横切能力天然属于 core。** 见 §3：修"停止按钮"必须同时改 `llm.py` 与 `pipeline.py`，
   插件**无法**自己修好。这类能力一出现，插件边界就被穿透了。

3. **"可选的后端模式"没带来选择价值。** 图片输入是核心能力（拍照搜题是最自然的用法），
   代价却是"要开图片就换一个启动脚本"。而且实测踩过一次：8000 上跑的是旧 target，
   `/api/vi/health` 直接 404，**不报任何错**。

> **插件形式什么时候是对的**：只对那类"实验性 / 高危 / 随时可能删"的功能
> （如 `planner_worker` 已实测证伪、`remote_access` 默认关）。
> 判据一句话：**"这个功能是否要常驻、是否要被别人 import"决定它该在哪。**

### 1.4 三个必须知道的设计取舍

**① 图片先降采样，不是妥协是必需。**
手机照片 3~8MB、长边 3000~4000px，base64 后 ×1.37 → 请求体十几 MB，多数网关 413；
且视觉模型按**图块**计费，4000px 的图块数是 1568px 的 6 倍而准确率不再提升。
策略是**先降质量、再降尺寸**（可辨识度主要由尺寸决定）。

**② 两个隐蔽坑已处理**（`vision.py` 里都有注释）：
- **EXIF 方向**：手机竖拍照片像素其实是横的，不处理 → 模型看到"躺着的题目"，**不报错但识别质量明显下降**
- **透明底变黑**：带 alpha 的 PNG 直接 `convert("RGB")` → 透明区 RGB 是 (0,0,0) → **黑底黑字**，模型什么也读不出来。必须先合成到白底

**③ 图片不落盘、不进历史。**
会话里只留摘要（尺寸 + sha256 前 16 位）。一张 base64 图几百 KB，存进会话会让
`/api/threads/<id>` 返回几 MB 的 JSON。**代价**：刷新后看不到"当时发的那张图" ——
这是**刻意的诚实降级**（图片从未上传到任何持久存储），比"假装能回显"好。

## 2. 图片输入踩的两个坑（都是"自己人关掉了功能"）

### 2.1 黑名单误判：`deepseek-chat` 其实能读图

**症状**：用户切到 `direct` 档后传图，被闸口拒绝，提示"当前模型不支持图片输入"。
用户原话是**"怎么可能，应该能读的啊"** —— 用户是对的。

**根因**：`vision.py` 的黑名单里写着 `"deepseek-chat"`，依据是"DeepSeek 对话/推理模型
没有视觉能力"。**那是过时的印象，不是事实。** 实测（绕过闸口直接发多模态请求）：

| 模型 | 实测 |
|---|---|
| `deepseek-chat` | ✅ **能读** — 0.8s 准确读出 `x^2 - 5x + 6 = 0` |
| `deepseek-flash` | ✅ **能读** — 1.2s |
| `deepseek-v4-pro` | ❌ 不能，但模型**自己说明**"无法识别图片内容" |

**修法（改的是判据，不只是名单）**：闸口该不该拦，判据是
**"接口报错可不可读"**，不是"模型行不行"：

```
误拒（能读却拦下）→ 用户彻底失去功能 + 收到误导提示   ← 本次踩的
误放（不能读却放行）→ 多花一次往返，拿到一句（通常可读的）报错
```

**误拒的代价远大于误放。** 现在 `_looks_text_only()` 的判定顺序是：
1. `_VERIFIED_VISION` 实测白名单（**最高优先级**，压过所有猜测）
2. 名字带 `-vl` / `vision` / `gpt-4o` 等视觉特征 → 放行
3. 黑名单只留**未实测的保守条目**（llama / mistral 那一代）
4. **拿不准一律放行**，让接口去说话

> ⚠️ **改这一块时的警告**：清理名单别"整批删"。我第一版把同批的 `llama-3` / `llama2`
> 一起删了 —— `llama-3-70b` 立刻被放行（那是回归）。闸口回归脚本（15 个型号）当场抓到。

### 2.2 `deepseek-chat` 是遗留别名（顺带查清）

用户问"为什么 direct 档写的是 `deepseek-chat`，不应该是 `deepseek-flash` 吗"。

| 探测 | 结果 |
|---|---|
| `GET /models` | 只列 `deepseek-flash` 和 `deepseek-v4-pro` |
| 请求 `model=deepseek-chat` | ✅ 接受，但**响应回显 `model=deepseek-flash`** |
| 请求 `deepseek-chat-x` | ❌ 400：`The supported API model names are deepseek-flash, deepseek-v4-pro` |

**`deepseek-chat` 是官方兼容旧代码的遗留别名，实际路由到 `deepseek-flash`。**

⚠️ **关键差异：别名隐含关掉了思考**（同一 prompt、预算给足）：

| 请求 model | 回显 | reasoning_tokens | 耗时 |
|---|---|---|---|
| `deepseek-chat`（别名） | `deepseek-flash` | **None** | 0.59s |
| `deepseek-flash`（真名） | `deepseek-flash` | **51** | 0.87s |
| `deepseek-flash` + `thinking:{type:disabled}` | `deepseek-flash` | **None** | 0.61s |

**所以"只改名字"会让模型开始思考，必须同时显式关掉（或开着，看你要什么）。**
现在配置里用的是**真名 + 显式开关**，行为不再依赖别名。

## 3. 停止按钮停不掉模型（真 bug，已修）

### 3.1 症状与根因

用户反馈"停止按钮并没有真停止模型思考"。

**根因**：`api/pipeline.py::Canceller` 原本只登记**渲染子进程**（`_procs`，靠 `proc.kill()`）。
而 LLM 调用是**另一条路径** —— `for raw in resp:` 阻塞读 HTTP 流，
**登记处里没有任何东西属于它**。所以点停止后：

1. 浏览器连接断开 → `stream()` 的 `finally` 确实调了 `cancel()`
2. 但既没有进程可 kill、也没有连接可关 → 工作线程继续阻塞在 read 上
3. **模型继续吐 token、继续计费**；`push()` 因事件循环已关而静默丢弃
4. 最后还会把整份结果落盘

**用户以为停了，账单和 CPU 都不同意。**

### 3.2 修法与两个关键坑

| 改动 | 位置 |
|---|---|
| `Canceller` 新增 `watch(obj)` / `unwatch(obj)`（`close()` 语义），与 `register()`（`kill()` 语义）并列 | `api/pipeline.py:112` |
| `LLMCancelled` + ContextVar 取消令牌（`set_cancel_token` / `check_cancelled`） | `storyboard/llm.py:56,91,94,118` |
| 流式与非流式**两条** HTTP 读取路径都登记 `resp`，循环每轮检查 | `storyboard/llm.py:520,885` |
| `pipeline.stream()` 在**工作线程体内**设置令牌 | `api/pipeline.py:660` |

**坑 ①：`LLMCancelled` 故意不继承 `LLMError`。**
代码里遍布 `except LLMError`，那些分支的语义是"这次失败，换个方式再来一遍"——
尤其 `stream_storyboard` 有一条"流式不可用 → 退回非流式重试"的降级。
取消若被当成 `LLMError`，用户按"停止"会换来**立刻再发一次完整请求**：
等更久、花更多钱，比不修还糟。不继承它，事件才会穿过所有 except，落到 `pipeline` 被单独接住。

**坑 ②：取消时抛的不是 `OSError`，是 `AttributeError`。**
第一版按 `except (OSError, HTTPException)` 处理，测试直接失败：
`close()` 把 `resp.fp` 置成 `None`，而读线程正阻塞在 `fp.peek()` 上，抛的是
`AttributeError: 'NoneType' object has no attribute 'peek'`。
正确顺序是**先问令牌"是不是取消了"，再决定怎么包装异常**。
（这个坑不实测根本发现不了。）

**坑 ③（必须记住的实现约束）**：ContextVar **不会自动进入新线程** ——
必须在**线程体内**`set`，在外面设完再起线程，线程里拿到的是 `None`，
于是 `check_cancelled()` 永不触发，"停止"又静默失效**且不报错不打日志**。

### 3.3 顺带修掉：`replace-scene` 阻塞事件循环

同一根源发现的另一个 bug：`api/routes/storyboard.py` 的
`llm.regenerate_scene()` 原先**直接在事件循环里同步调用**，没走 `pipeline.stream`：

- 收不到取消令牌 → 用户点停止完全无效
- **整个服务在那十几秒（实测 98.4s）里是"哑"的** —— 连 `/api/health` 都排不上队

已改为包进 `pipeline.stream`（`run()` 在工作线程执行、结果用单槽 dict 带出）。
实测修复后：`replace-scene` 进行中 `/api/health` **0.03s** 返回。

### 3.4 验证

| 判据 | 结果 |
|---|---|
| 断开后留档出现 `error="用户已停止生成（cancelled）"` | ✅ |
| 服务端日志打出"客户端停止，已中断模型调用"，且**无 traceback** | ✅ |
| 断开后留档计数**停止增长**（没把那一轮跑完） | ✅ |
| 取消后服务仍健康 | ✅ |

> ⚠️ **判据上的一个误区**（下次测试别再踩）：不能用"留档里有没有 cancelled"当唯一判据 ——
> 取消可能恰好发生在一轮刚正常结束、还没进下一轮的时刻（那时没有 cancelled 记录，
> 但确实停了）。**"断开后不再产生新记录"才是"停止生效"的可靠判据。**

## 4. 另一个真 bug：「思考到几万字就卡住，过半天大纲突然出现」

**症状**：用户反馈"深度思考思考到几万字（有的是 2 万有的是 3 万）然后就卡住了，
过了半天后分镜大纲突然就有了"。日志物证：`attempts=4`（跑满了 4 轮）。

**根因：重试轮被降级成了非流式，而非流式没有任何进度事件。**

`stream_storyboard()` 里每条回灌重试路径后面都跟着 `use_stream = False`
（共 4 处：截断 / JSON 解析失败 / brief 为空 / 校验失败）。于是：

```
第 1 轮  流式    → 思考流推给前端（界面在动，用户看到"思考 2 万字"）
    ↓ 校验失败
第 2~4 轮 非流式 → 一个事件都没有（界面完全静止，几分钟）
    ↓ 好不容易通过校验
界面才突然出现大纲
```

**为什么难认**：日志里 `streamed=True` 是**首轮**的值，看起来像"全程都流式了"，
于是排查方向被带到"上游卡住了"——**真正发生的是我们自己关掉了流式。**

### 修法：把"要不要流式"与"要不要把正文推给用户"解耦

这两件事原先被绑在一起（"重试 → 非流式"），但诉求完全不同：

| 诉求 | 结论 |
|---|---|
| 重试期间**要有进度信号** | 必须保持流式（思考流是那几分钟里唯一在动的东西） |
| 重试期间**不要再吐正文** | 必须不吐（brief 会重写，再吐一次就是同一段话说两遍） |

所以：4 处回灌重试**不再**关流式；`on_reasoning` 改成**每轮都转发**；
`on_delta`（正文）收紧成**只有第一轮**。`use_stream = False` 只保留在唯一该保留处 ——
连一个字节都没收到的"网关真不支持 stream"降级。

**验证**：用**假网关**做确定性验证（真实回灌是随机触发的，靠运气测不到）：
首轮返回坏 JSON 触发重试，两轮都发思考流。
修复前第 2 轮无思考、修复后有。真实链路复测 83.8s、`thinking_delta` **16701 个事件**、
全程无 >8s 静默。

## 5. 模型配置：两个档对齐 + max_tokens 定值

### 5.1 一个重要事实：两档其实是**同一个模型权重**

用户指出：`relay`（中转站 `deepseek/deepseek-v4.1-flash`）与 `direct`（官方
`deepseek-flash`）**是同一个权重**，relay 只是"官方模型 + 开了思考 + 中转"。

这推翻了我原先"两档是不同模型"的假设。实测确实如此：

| 探测 | 结果 |
|---|---|
| 官方 `deepseek-flash` **默认** | `reasoning=59` → **本来就开思考** |
| 官方 `thinking.enabled` / `reasoning_effort=high` | 都能开 ✅ |
| **官方 max_tokens 上限** | 支持到 **131072** |
| 中转站上限 | 支持到 262144 |

### 5.2 质量差距是真的（这条很关键）

**先前我用整体平均得出"direct 几乎不差"，那是错的** —— 样本混了不同题目。
按**同一道题**配对后差异明显（尤其最后一题）：

| 同题 | direct（当时关着思考） | relay（开思考） |
|---|---|---|
| 面积法证勾股 | 6 镜 / 31 元素 / `polygon` `rect` | 4 镜 / 28 元素 / `polygon` **`brace`** |
| f(x)=x³-3x 极值 | 4 镜 / 24 元素 | **5 镜** / 19 元素 / **多了 `table`** |
| **读图解题** | 4 镜 / 17 元素 / **0 个图形元素！** | 3 镜 / 24 元素 / **`axes` `plot` `dot` `line` `tracker`** |

最后一题最能说明问题：**同一张图，关掉思考后一个图形元素都不用**（纯堆了 14 个公式和文字），
开着思考才老老实实画坐标系、曲线、动点、切线。
即**关思考会让模型倾向"直接把答案摆出来"，而不是"想清楚怎么把过程画出来"**。

> ⚠️ 诚实说明局限：`deepseek-flash` 与 `v4.1-flash` 即使同权重，"关思考"与"模型本身"
> 各占多少这份数据分不出来；且 direct 样本只有 6 条。**但既然质量重要，就不该关思考。**

### 5.3 最终配置（`llm.local.json`）

```json
"active": "relay",
"profiles": {
  "relay":  { "model": "deepseek/deepseek-v4.1-flash", "max_tokens": 65536, ... },
  "direct": { "model": "deepseek-flash", "max_tokens": 65536,
              "extra_body": { "thinking": { "type": "enabled" } }, ... }
}
```

**用法**：**主力 relay**；中转站卡的时候切 `direct` 应急（正式演示建议用 direct，
少一层中转更稳）。两档**已对齐**（都开思考、同一份 `max_tokens`），切换不改变产物质量。

### 5.4 max_tokens 为什么是 65536（有数据支撑）

用留档 100 条**带思考**的真实调用统计：

| 分位 | 思考 token | 总输出（思考+正文） |
|---|---|---|
| P50 | 5673 | 8091 |
| P90 | 17519 | 20890 |
| **P95** | **22956** | **25220** |
| 最大 | 32384 | **32768**（正好撞顶） |

原来的 32768 是"刚好卡在边缘"：能盖住约 99%，但**确实撞过顶**（1/108），
代价是触发一整轮回灌重试（≈46s + 9027 token）。

**关键点：`max_tokens` 是上限、不是预分配。** 实测印证：

```
max_tokens=65536 | completion=20479 (31% of cap)   ← 只按 20479 计费
max_tokens=65536 | completion=5546  ( 8% of cap)   ← 只按 5546 计费
```

所以加大**不增加日常成本**，只在思考暴走时多花钱 —— 而那正是你希望它能想完、
而不是被截断重来的情况。

### 5.5 顺带新增：`extra_body` 透传槽位

"关思考"这类参数**不是 OpenAI 标准**，各厂商名字都不同
（DeepSeek `{"thinking":{"type":"disabled"}}`、别家 `enable_thinking` /
`reasoning_effort` …）。在代码里硬编码任何一家都会误导下一家适配，所以做了个透传槽位。

⚠️ **三处必须同时改，漏一处就是静默失效**（正是 `HANDOFF §8.2` 那个坑的形态）：
1. `cfg` 默认值里要有 `"extra_body": {}`
2. `_merge_cfg()` 要**显式处理 dict**（和 `headers` 同理）——
   下面那行 `if k in cfg` 只放行**已有键**，而 `extra_body` 的子键都不在 cfg 里
3. `_merge_extra_body()` 用 **`setdefault`**（不覆盖标准字段），且必须在
   `llm_log.cache_key()` **之前**调用 —— 否则改了开关会命中旧留档指纹

启动横幅也加了 `LLM 私有 : {...}` 一行（"模型为什么在思考"是最难靠猜的事）。

**实测过的关思考写法**：

| 写法 | 结果 |
|---|---|
| `{"thinking": {"type": "disabled"}}` | ✅ 有效 |
| `{"reasoning_effort": "none"}` | ✅ 有效 |
| `{"enable_thinking": false}` | ❌ 无效（照样思考） |
| `{"thinking": false}` | ❌ 400（要的是对象，不是布尔） |
