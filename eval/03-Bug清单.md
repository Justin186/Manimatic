### BUG-001 分镜之间不清屏，导致内容重叠

- **发现者**：用户
- **发现时机**：跑 `lim_taylor.json`，答案页
- **现象**：`summary_card` 的"极限 = 1/2"等文字，与上一个分镜 `step_card` 的板书内容叠在一起
- **根因**：`renderer.py` 的 `render()` 拼接分镜代码时**没有任何清屏逻辑**。
  之前 `title_card` / `axes_plot` 等模板各自末尾写了 `FadeOut`，掩盖了缺陷；
  `step_card` 改成累积板书后需要保留内容到本分镜结束，于是下一个分镜直接叠上去。
- **修法（架构层）**：在 `renderer.py` 每个分镜代码块前统一插入
  ```python
  if self.mobjects:
      self.play(FadeOut(Group(*self.mobjects)), run_time=0.35)
      self.clear()
  ```
- **为什么不放在模板里**：清屏是"分镜之间"的规则，不是"某个模板"的规则。
  放在渲染层，任何模板（包括以后新加的）都不可能漏掉。
- **状态**：✅ 已修（commit 25ee583）
- **对应清单条目**：第 7 条
- **后续（2026-09-16）**：这条"分镜之间统一清屏"是**对的默认**，但它同时也让
  「连贯内容」没法表达 —— 见 BUG-008。现在清屏仍然默认生效，**想延续的元素用
  `carry` 显式豁免**。

### BUG-006 中文 Windows 下 subprocess 读取 manim 输出崩溃

- **发现者**：用户本机跑 run_all.bat
- **现象**：`UnicodeDecodeError: 'gbk' codec can't decode byte ...`；多数题渲染成功但输出报错，c2 一题卡死需 Ctrl+C
- **根因**：`generate.py` 的 `subprocess.run(text=True)` 未指定编码，中文 Windows 用 GBK 解码 manim 的 UTF-8 输出。**AI 侧沙箱 locale 是 UTF-8，所以 AI 跑不出这个 bug** —— 环境相关 bug 只有真机才暴露。
- **修法**：`subprocess.run(..., encoding="utf-8", errors="replace")`
- **状态**：✅ 已修
- **教训**：凡涉及 subprocess 文本输出，encoding 必须显式指定，`errors="replace"` 兜底。

### BUG-007 HEADER.format() 把代码模板里的花括号当占位符

- **发现者**：AI（改 rich/formula 后首次渲染）
- **现象**：`KeyError: '顶点'` / `KeyError: 's'`
- **根因**：HEADER 是经 `.format()` 处理的模板字符串，函数体 docstring 里的 `\text{顶点}`、f-string 里的 `f"${s}$"` 都被当占位符解析
- **修法**：HEADER 内字面花括号一律写成 `{{ }}`
- **状态**：✅ 已修
- **教训**：用字符串模板生成代码时，模板内一切非占位符花括号都要转义；这是这类"代码生成器"的经典坑。

### BUG-008 每个分镜末尾都淡出 → 连贯内容只能每镜重画一遍

- **发现者**：用户
- **现象**：讲二分查找时，**每一镜都重新画一遍数组**；分镜末尾一律淡出，
  连贯过程看起来像"从头再来"
- **根因**：三处叠加，**不是模型的锅** ——
  ① `renderer.py` 的 `_CLEAR` 在分镜 2..N 之前无条件 `FadeOut(全部) + clear()`；
  ② `dsl.build_scene()` 每分镜**独立重新构建**元素；
  ③ `_norm_action()` 要求 `target` 在**本分镜**的 `declared` 里，跨分镜引用直接报错。
  **所以改 prompt 治不好** —— 写什么提示词，`_CLEAR` 都照淡不误
- **修法**：DSL 加显式延续标记 `{"id": "arr", "carry": true}` + 三条硬校验
  （分镜 1 不许写 / 必须在上一镜结束时真的在屏上 / 依赖要一起承接）。
  **刻意不做自动识别**：两段独立例题都用 `ax`/`plot` 时会被误判，`create` 动画凭空消失
- **状态**：✅ 已修（`HANDOFF.md` §8.32，`tests/test_carry.py` 11 条）
- **对应清单条目**：第 7 条（清屏）的正面对手；也是「画面连贯性」的第一条

### BUG-009 校验层一次只报一个错，4 次重试被耗光

- **发现者**：AI（排查重试耗尽时）
- **现象**：一份散着两三个错的分镜，会「报一个 → 模型改一个 → 又撞下一个」，
  最后报"连续 4 次都没能产出通过校验的分镜"
- **根因**：`validate_scene()` 是**遇到第一个错就抛**，而模型本来能一次改完所有错 ——
  是反馈带宽把它逼死的
- **修法**：收集 elements / timeline / 表达式三处的问题一次回灌。
  ⚠️ 两个坑：失败元素的 id 仍要尽力登记进 `declared`（否则级联报"未声明"，
  假错误淹掉真问题）；失败元素的表达式仍要只读扫一遍（否则只报前一个错）
- **状态**：✅ 已修（`HANDOFF.md` §8.28）
- **对应清单条目**：D7 门「三次内成功率 ≥95%」

### BUG-011 `brief` 为空能一路绿灯；`brief` 不在第一个键没人知道

- **发现者**：AI（过 prompt 与校验层时发现）
- **现象**：① `brief` 为空时生成"成功"，但用户什么都看不到
  （纯概念问答时它更是**唯一**产出）；
  ② 厂商把 JSON 键序重排后，前端流式期间一个字都不出，**且不报任何错**
- **根因**：`_norm_brief()` 只做 `strip()[:500]`，**空字符串合法**；
  而"键序"只有 prompt 里一句自然语言叮嘱，没有任何校验或告警
- **修法**：① `brief` 为空 → 回灌重试（配专用反馈）；
  ② 键序错 → 打 `[WARN]`，**刻意不重试**（重试轮走非流式，换不回"秒级见字"，
  只会白花一次调用）；
  ③ 加**兜底补发**：整条链路走完一个字都没吐出去时，校验通过后把 brief 整段补发
- **状态**：✅ 已修（`HANDOFF.md` §8.29）
- **对应清单条目**：「秒级见字」这条产品承诺

### BUG-012 成品模板化：每道题都长一个样，几何题也上坐标系

- **发现者**：用户
- **现象**：出错率已经很低，但**成品模板化严重** —— 结构永远是"封面 → 图形/推导 → 结论"，
  画面永远是一张坐标系 + 一条曲线 + 一个动点
- **根因**：**在 prompt 里**，不在模型上 ——
  ① 规范里写死了一条固定结构配方；
  ② 唯一的 few-shot 示例就是"坐标系 + 曲线 + 切线"，而模型对示例的模仿远强于对规则的遵守；
  ③ prompt 里**没有一句话**告诉模型"这道题的画面引擎是什么"
- **修法**：删掉固定配方 → 改成「先判题型，再决定画面引擎」+ 三条反模板硬要求；
  few-shot 从 1 个补到 4 个（含**全程不用 `axes`** 的几何题）；
  顺带修掉"每个分镜 4~12 秒"这条**比校验层更严**的约束（它逼着模型把连续过程切碎）
- **状态**：✅ 已改（`HANDOFF.md` §8.31）—— **效果待真实题目验证**
- **对应清单条目**：D7「内容正确率（人工看画面）≥90%」；这是"画面质量"类问题的第一条

### BUG-013 同一个元素反复 `replace` 之后，旧文字被重新加回屏上叠成一团

- **发现者**：用户（"现在渲染还是不能避免重叠啊"）
- **现象**：二分查找那题，分镜 2 底部**4 行不同的提示文字叠在同一位置**
  （`7 < 15，说明…` / `范围缩到 4~7…` / `11 < 15…` / `范围只剩 6~7…` 糊成一团）。
  日志正常、无报错、校验全过
- **根因**：`replace` 的代码生成把 `target` 的**原始变量**当成替换源，第二次起就错了 ——
  `ReplacementTransform(_e_info, _e_i2)` 会把 `_e_info` 移出场景，之后
  `ReplacementTransform(_e_info, _e_i3)` 的源对象**已经不在屏上**，而 manim 的
  `Scene.add_mobjects_from_animations()` 有一条"被动画却不在场景里的对象**重新加回场景**"
  （`scene.py`：*Anything animated that's not already in the scene gets added to the scene*）。
  于是每替换一次就多叠一层。**模型写的 JSON 没错，是我们的代码生成错了**
- **修法**：`_Builder` 加一层"id → 当前代表它的变量"的换绑（`_var()` / `self.alias`），
  `replace` 完成后把 `target` 换绑到 `into` 的变量上；所有"元素 id → 变量名"的地方统一走它
- **状态**：✅ 已修（`HANDOFF.md` §8.33）
- **对应清单条目**：第 18 条（替换后有没有叠影）

### BUG-014 `move_cells` 只挪不改大小 → `cell_box` 与网格严重错位

- **发现者**：抽帧（看 BUG-013 那段视频时顺带发现）
- **现象**：分镜 2 的蓝框声明是 `cols:[1,8]`（整张表宽），后面挪到 `cols:[8]`（只剩最后一格），
  结果一个 **8 格宽的蓝框被居中到最后一格上**：右边探出画面、左边横穿整张表；
  连 `[5,8]`、`[7,8]` 两次中间态也一样歪
- **根因**：`move_cells` 生成的是 `.animate.move_to(_cells_center(...))` ——
  **只挪中心、不改大小**，框永远是声明时的宽度。而校验层那条"框的大小不能变"的检查
  比的是 `len(rows)`/`len(cols)`（`[1,8]` 和 `[5,8]` 长度都是 2），**根本拦不住**
- **修法**：`move_cells` 改成 `Transform(框, _cell_box(表格, 目标行列))` ——
  位置**和大小**都由目标格子算出来。同宽就是纯滑动（卷积核那种），改宽就是重新贴合
  （二分查找候选范围逐轮减半那种），不需要分支。同时删掉那条失效的检查、
  并把 `scale`/`stretch`/`rotate` 也纳入"不许作用在 cell_box 上"（它们同样会破坏对齐）
- **状态**：✅ 已修（`HANDOFF.md` §8.33）
- **对应清单条目**：第 19 条（格框有没有贴合格子）

### BUG-015 表格"每行长度不一致"会穿透校验层，变成用户的 500

- **发现者**：AI（给 `T_TABLE` 加尺寸估算时发现的**存量静默失效**）

### BUG-016 底部字幕用形变替换，观感差（用户反馈）

- **发现者**：用户 —— "这个 ReplacementTransform 对这种底部字幕效果看起来不是很好，
  最好换个效果"
- **现象**：`replace` 只有一种实现（`ReplacementTransform`）：旧字**飞向**新字的位置
  再变成新字。字数一变，字幕就像被"揉"了一下
- **根因**：`replace` 的语义写死成"替换式**变形**"，没有别的过渡
- **修法**：`replace` 加可选 `effect`（`crossfade` 默认 / `slide` / `write` / `morph`）；
  **默认从形变改成交叉淡化**（四种效果的场景增删语义完全一致，所以 §8.33 的换绑逻辑不动）
- **⚠️ 实现时改了两轮，两次都是逐帧看出来的**：
  1. 最"标准"的交叉溶解是两半**全程**同时淡 —— 但底部字幕是**居中**的、两句字数常常不同，
     1.2s 的过渡里有 **0.4s 两句话糊在一起读不出字** → 改成"分段交接"（旧的前 60% 淡尽、
     新的从 40% 才淡入，重叠 20%）；
  2. 用户看完说**"淡出没淡出完淡入就来了"** —— 那 20% 的重叠在画面上就是"没淡完就来了"
     → 最终定成**严格先后、零重叠**（各占 `run_time` 的一半），逐帧序列里能看到
     中间有一帧**完全没有文字**
- **状态**：✅ 已修（`HANDOFF.md` §8.34）；逐帧复核：6 帧序列 = 旧的字渐隐 → 全空 → 新的渐显
- **对应清单条目**：第 20 条

### BUG-017 版面限制按"条数"而不按"尺寸"（用户反馈）

- **发现者**：用户 —— "现在格子的大小是不是被固定死了，还是更自由一些吧，
  而且还有什么一行不能超过几列这种，我觉得应该用更智能的方式判断会不会出界"
- **现象**：三类与尺寸无关的硬上限：表格最多 8 行 8 列、`cell_box` 格号最多 6 个、
  单元格最多 80 字。它们**两个方向都错**：
  - **拦不住该拦的**：8 列单字数字表宽 12.03（几乎顶满画面），8 列长公式表能到 30+，
    两者都是"8 列"，判罚一样；
  - **挡住了该做的**：`[1,2,3,4,5,6,7,8]` 选一整行完全正常，会被拒；
    80 字那条更糟 —— 它是**静默改内容**（写 90 字砍掉 10 字，没人知道）
- **另有一处"格子被固定死"的真身**：manim `Table` 的默认 `h_buff=1.3` 让**每个格子
  凭空比内容宽 1.3 个单位**，8 列光留白就吃掉 10.4 —— 而 DSL 一个尺寸参数都没暴露
- **修法**：新增 `storyboard/metrics.py`（纯算术估算器，无 manim 依赖）；
  三类硬上限全删，改成按内容估算尺寸、**估算明显超出画面才拒**，报错带"宽了多少 /
  减几列 / 字号降到多少 / pad_x 调小"；表格加 `cell_w`/`cell_h`/`pad_x`/`pad_y`
  四个可选参数（不写则生成代码逐字节不变）
- **状态**：✅ 已修（`HANDOFF.md` §8.34）。**"估算 ≥ 实测"这条不变式由 223 条标定断言盯着**
- **对应清单条目**：第 21 条

### BUG-018 贴边摆放的文字被护栏缩没（"有时候渲染出来的字特别小"）

- **发现者**：用户 —— "为什么现在有时候渲染出来的字特别小"
- **现象**：同一份分镜里有的字正常、有的小到看不清，甚至**整句消失**。
  特征是**时有时无**，取决于模型这次写的 `place.buff` 和文案行数
- **根因**：**在 `_fit()`（运行时兜底护栏）里，不在模型、也不在 `metrics`** ——
  §8.34 那一轮把它改成"按元素**当前中心**算对称可用空间"
  （`avail = 2 * min(中心 + 半边长, 半边长 - 中心)`），这对**居中**元素恰好等于
  12.4×6.6（当时只验证了这一种情形），但对 `place` 贴边摆放的元素是错的：
  它把 `_FRAME_MARGIN`（**居中内容的容量预算**）当成了"**画面有多大**"，
  于是对已经被 `place` 显式摆进边距里的元素**又扣了一次边距**。
  实测 `buff ≤ 0.7` 必命中：

  | `buff` | 算出的可用高 | 缩到 |
  |---|---|---|
  | 0.7 | 0.38 | 100% |
  | 0.6 | 0.18 | **48%** |
  | 0.5 | −0.02 | **0%（字消失）** |
  | 0.4 | −0.22 | **0%** |

  而 0.4 / 0.5 / 0.6 恰好是 few-shot 示例自己用的值，所以命中率高 —— 这就是"有时候"
- **为什么校验层没拦住**：**它不该拦**。那些文字远在 12.4×6.6 之内，
  `metrics` 放行是对的。是护栏自己重复扣了边距。
  ⚠️ 而告警文案当时写的是"校验层的尺寸估算没拦住它（见 metrics.py）"——
  **把排查方向带偏到估算器上**
- **修法**：判据改成"**画面**"，预算只用来给居中内容封顶
  （`room = min(2*min(半边长-中心, 半边长+中心), 预算)`）：
  居中 → 还是 12.4×6.6；贴边 → `room` 恰好 = 自身 + 2×buff → 恒不缩；
  中心已出画 → `room ≤ 0` → **只告警不硬缩**；另加 `_FIT_MIN_SCALE = 0.5` 下限
  （宁可留一截在画外，也不把内容缩成灰块）。告警改为自证
  "原始多大 / 缩到多少 / 画面多大 / 该改哪里"
- **状态**：✅ 已修（`HANDOFF.md` §8.39）
- **验证**：`tests/test_fit_layout.py` 15 条 + 全量 148 passed；
